## Verdict

**FAIL — do not release.** The public site serves the candidate and the product behavior is strong, but one mandatory claim fails against fresh Azure state. The active rollout is unhealthy and has lost the required one-replica/durable-volume topology. New clinics also cannot buy any offered plan because the exact Sociobot checkout URLs return HTTP 500, which prevents subscription-gated live dispatch. A caller can bypass API quotas by choosing a different first `X-Forwarded-For` value on each request.

No product code was changed during verification.

## Release-blocking findings

### Critical — the declared production rollout is unhealthy and unsafe

The exact `.factory/claims.json` command for `single-replica-durable-topology` failed. Its checked-in topology assertion passed, then `npm run verify:deployment:current` failed because the live Container App template does not set both replica bounds to one.

Fresh Azure evidence:

- Latest revision: `sf-clinic-reminder-proof--0000063`
- Latest ready revision: `sf-clinic-reminder-proof--0000062`
- `0000063` is active and has traffic weight 100, but its health is `Unhealthy`, running state is `ActivationFailed`, and Azure reports `Deployment Progress Deadline Exceeded. 0/1 replicas ready.`
- `0000063` uses the short image tag `sociobotregistry.azurecr.io/sf-clinic-reminder-proof:d65c4001e076`, has `minReplicas: 1`, `maxReplicas: 3`, and has no volumes or volume mounts.
- Healthy fallback revision `0000062` has traffic weight 0 in control-plane metadata, but it is what public ingress serves. It uses the full candidate image tag, one replica, and both required Azure Files mounts.

This is not a stale report: the control plane was queried during this verification. Public requests currently succeed only through Azure's fallback behavior. The running state contradicts the README promise that production is pinned to one replica with durable and backup mounts, and it makes the in-process limiter and SQLite topology unsafe if the bad template ever activates.

Required fix: deploy the full 40-character candidate image through `npm run deploy:container`, preserve both mounts and `minReplicas=maxReplicas=1`, wait for that revision to become healthy and solely traffic-bearing, then rerun `npm run verify:deployment:current`.

### Critical — a new clinic cannot activate the subscription required for live dispatch

The application requires an `active` or `grace` Sociobot subscription before it sends a live reminder. Fresh requests to the exact checkout URLs generated by the backend returned HTTP 500 with `{"error":"Internal server error","status":500}` for all three offered tiers on both `pilot-api.sociobot.in` and `api.sociobot.in`: `clinic`, `practice`, and `network`.

The backend converts that upstream result to `503 billing_product_unavailable`. Therefore a new clinic cannot pay and cannot reach the brief's real provider-dispatch job. Fixture-backed billing tests pass, but they do not make the production billing catalog usable.

Required fix: enable the product and recurring tiers in the Sociobot billing catalog, then complete a real hosted test checkout, return, subscription verification, cancellation, and revocation flow.

### High — a client can bypass every per-IP allowance by spoofing `X-Forwarded-For`

The nominal production boundary works when the client does not supply the header: one network client received five `200` workspace creations, then two `429` responses with `Retry-After: 3599`.

The backend trusts the first `X-Forwarded-For` value. From the same verifier and connection path, seven more creation requests each supplied a different first value; all seven returned `200`. The live ingress therefore does not replace the caller-controlled first hop. The general and billing limiters use the same extractor, so their quotas are bypassable in the same way.

Required fix: strip caller-provided forwarding headers at the trusted ingress or derive the client key from an ingress-authenticated hop. Add a live regression proving one physical client cannot create fresh buckets by changing request headers.
